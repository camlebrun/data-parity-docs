Five suites, from fast to complete (the fifth needs a real BigQuery project and is not part of CI). Run the first after any change in `src/`, the others after any change in
`dbt_package/`. Only the last one touches BigQuery.

| Suite | Command | Covers |
|---|---|---|
| pytest | `python -m pytest -q` | Unit tests and CLI tests with a fake dbt; always run. With `DBT_FUSION=dbt` (or `DBT_CORE`), `tests/test_integration.py` also runs against the real test bed. |
| `test_reconcile.sh` | `sh integration_tests/test_reconcile.sh` | End-to-end CLI against the ground truth; dbt-core and Trino scenarios when `DBT_CORE` / `TRINO=1` are set. |
| `test_cache.sh` | `bash integration_tests/test_cache.sh` | The closed-partition cache macros. |
| `test_config_guards.sh` | `bash integration_tests/test_config_guards.sh` | Bad or ambiguous arguments and model configs must fail loudly or be read correctly. |
| `test_bq_trino.sh` | `BQ_PROJECT=<project> DBT_CORE=<dbt-core> PY=<python> bash integration_tests/test_bq_trino.sh` | A real BigQuery dataset against Trino tables, see [below](#real-bigquery-vs-trino). |

## The test bed

`integration_tests/` holds two simulated engines: two DuckDB files, schema `mart`, with the same logical tables:
`orders` (about 200,000 rows, partitioned by `order_date`, 120 days), `customers` (about 5,000 rows, no date) and
`events_nopk` (about 20,000 rows, no primary key). `engine_a` is the reference; `engine_b` carries deliberate
corruptions. The data is deterministic (derived from a hash of `order_id`, no random generator, no clock), generated by
`generate.py` and git-ignored.

```bash
uv run --no-project --with duckdb python integration_tests/generate.py
cd integration_tests
dbt deps
dbt run --target engine_a      # the models are tables: build them on both targets
dbt run --target engine_b
data-parity run --a engine_a --b engine_b
```

Run from `integration_tests/`: the DuckDB paths in `profiles.yml` are relative to it.

`generate.py` writes the DuckDB files with `storage_compatibility_version` set to `v1.0.0`, so dbt Fusion can read them
whatever DuckDB version built them (the previous "unreadable, storage version 999" warning no longer applies; this
page's author regenerated them with DuckDB 2.0.0 and dbt Fusion 2.0.9 built both targets). The models are tables that
**must be built** with `dbt run --target engine_a` and `dbt run --target engine_b` before `data-parity run`.

## Ground truth

| # | Table | Partition | Corruption | Must be flagged |
|---|---|---|---|---|
| a | orders | 2025-01-11 | 3 rows missing in B | yes (counts differ) |
| b | orders | 2025-01-21 | `amount` +0.01 on 2 rows | yes (same count, hash differs) |
| c | orders | 2025-01-31 | `status` `'paid'` vs `'paid '` on 1 row | yes (trailing space is significant) |
| d1 | orders | 2025-02-10 | `price_float` relative noise 1e-12 on all rows of the day | **no** (tolerated by scale-6 rounding) |
| d2 | orders | 2025-02-20 | `price_float` +0.01 on 2 rows | yes |
| e | orders | 2025-03-02 | 1 extra row only in B | yes |
| f | customers | none | `city` NULL in A vs `''` in B | yes (NULL differs from empty) |
| g | all three | all | `meta_loaded_at` differs on every row | **no** (`meta_` excluded) |
| h | orders | 2025-03-12 | identical rows, inserted in another physical order | **no** |
| i | events_nopk | 2025-01-06 | one row with `value` + 1 (10 legitimate duplicates exist in both) | yes |

So `orders` must report exactly 5 differing days (2025-01-11, 01-21, 01-31, 02-20, 03-02); `customers` one table-level
difference; `events_nopk` one differing day. Row counts: orders 200,000 vs 199,998; customers 5,000 / 5,000;
events_nopk 20,010 / 20,010. The report of the real run is in
[Reading the report](/data-parity-docs/getting-started/reading-the-report/).

## What each script asserts

**`test_reconcile.sh`**: DuckDB A vs B (exit 1, the five days with kind and column, `customers.city`,
`events_nopk.value`); `engine_a` vs itself (exit 0); error exit codes (unknown target, misspelled model: 2); `--last 5`
gives exit 0 with `scope_limited` and *ISO on the checked scope* while the whole run exits 1; one `group by dp_p` in the
compiled pass-1 SQL; dbt-core gives the same per-model results as Fusion (`DBT_CORE`). With `TRINO=1` (Docker Trino on
`localhost:18080`, catalog `memory`): `load_trino.py` loads the same fixtures into `memory.dp_a` and `memory.dp_b`,
`trino_project/` (dbt-core only) exposes them as views, DuckDB A vs Trino `dp_a` must be identical and vs `dp_b` must give
the same per-model results as DuckDB A vs B.

```bash
PY=python3 DBT_CORE=<dbt-core binary> TRINO=1 sh integration_tests/test_reconcile.sh
```

**`test_cache.sh`** works on copies of the databases (originals never written):

| Step | Proof |
|---|---|
| reference | an independent plain grouped query |
| (a) | dry run lists what it would insert; the schema does not exist afterwards; `write: true` without schema is refused |
| (b) | `write: true` stores 192 rows (96 closed days for each of two models) |
| (c) | `cached_pass1` is byte-identical to the reference and to `data_parity_reconcile` level 1 |
| (d) | a second refresh is "up to date" |
| (e) | a rewrite of one closed day is **not** visible in the cached pass 1 (the danger); `cache_verify` reports exactly 1 STALE and fails |
| (f) | a new column or a version bump: nothing trusted, output identical to live |
| (g) | the compiled SQL shows the only hash scan filtered to the open days |

```bash
PY=<python with duckdb> DBT=dbt bash integration_tests/test_cache.sh
TRINO=1 PY=<python with duckdb+trino> DBT2=<dbt-core> bash integration_tests/test_cache.sh
```

**`test_config_guards.sh`**: string `exclude_prefixes` / `exclude_columns`, `only` (string, unknown names), `partitions`
shapes, `cached_pass1` refusing `as_of` / `partitions`, the NULL partition sentinel, the `write` flag, schema and
`lag_days` validation, `data_parity: false`, and the unsupported `target.type` guard. All in a throw-away copy.

## Real BigQuery vs Trino

`integration_tests/test_bq_trino.sh` checks the shape of a real migration with no emulator: the dbt project of
`integration_tests/bq_project/` runs on **real BigQuery** (side A) and is compared to Trino tables (side B) read with
`--schema-b`. Tables are named and typed like a production warehouse (`fct_orders`, `dim_customers`, `fct_events`;
native DDL with `INT64`, `NUMERIC(18,2)`, `FLOAT64`, `TIMESTAMP`, `BOOL`; `MONTH` partition on `order_date`, clustering).
The data is the same as above, loaded into a throw-away dataset `mart_parity_test` (EU, expires after one day), and Trino
holds a reference copy and a corrupted copy.

| Check | Expected |
|---|---|
| conformance, BigQuery vs Trino | hash identical |
| BigQuery vs the reference copy | every model ISO |
| BigQuery vs the corrupted copy | exactly the 5 days of `fct_orders`, `city` in `dim_customers`, 2025-01-06 in `fct_events`, nothing on `meta_loaded_at` |

Requirements: a GCP project (`BQ_PROJECT`, required: no project id is hard-coded), `gcloud auth application-default
login`, a dbt-core with both `dbt-bigquery` and `dbt-trino`, and a Trino with a `local` catalog (memory connector). Cost
is about 0 € (20 MB stored, free loads, reads under 1 GB per run). The script **deletes nothing**: if the dataset exists
it stops; `REPLACE=1` drops and recreates it, `CLEANUP=1` drops it at the end. It needs a GCP project, so it is not part of CI.

The memory connector has no partitioning or clustering, so the production partition layout cannot be tested on the Trino
side.

## Docker Trino

The Trino scenarios need a container named `dp-trino` publishing port 18080 and dbt-core with dbt-trino. Only the
`memory` catalog is used. This is why real-cluster behaviour is untested.
